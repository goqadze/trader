03 · The decision pipeline

One POST /signal, five LangGraph nodes

Every decision, from a backtest day or a live bot, runs the same compiled graph in decision-service/app/agent.py. It's a straight line: each node reads the shared state and returns only the keys it changes.

START
→
1 DATAfetch_data

~420 days of daily bars from Yahoo up to as_of; a 10:00 replay rewinds the day to 30-minute bars. The strategy's analyze() turns them into facts (SMA, RSI, ADX, swings...).

→
2 LLMnews_rag

Fetch news → embed → store in pgvector → retrieve the 8 most relevant + recent → the LLM labels it bullish / bearish / neutral. Skipped when news=false.

→
3 RULEdecide

The strategy's decide() picks BUY / SELL / HOLD. News that agrees adds +0.15 confidence, news that conflicts −0.15. The LLM never decides the trade.

→
4 RULEsize_position

For a BUY: stop and target from the entry, shares from fixed-fractional risk (risk 2% of the account to the stop).

→
5 LLMexplain

Two sentences for a human. Backtests send explain=false and get the rule text instead (thousands of decisions, no token bill).

→
END

The state that flows through

class State(TypedDict, total=False):
    symbol, as_of, decided_at, strategy
    account_balance, stop_pct, target_pct
    use_news, llm_explanation     # switches
    indicators                    # node 1
    headlines, catalysts, sentiment  # node 2
    action, confidence            # node 3
    position                      # node 4
    reasoning                     # node 5
    steps: list[str]              # "show your work"

The steps trail is what the activity log shows: every node appends one line.

Why a workflow, not an “agent”

An autonomous agent lets the LLM choose which tool to call next, in a loop. Here the code fixes the order and the rules decide; the LLM only reads headlines and writes prose. That makes decisions:

  • reproducible: same settings, same result (temperature 0, saved news judgments)
  • testable: a rule is a pure function of the facts
  • cheap: one small LLM call per symbol-day, none when technical only
  • safe: a hallucination can tilt confidence by 0.15, never flip a rule
04 · LangGraph & LangChain

What each library does here (and what it doesn't)

Both are used lightly on purpose. Pinned to the 0.3 generation (langgraph<0.3, langchain<0.4) because Langfuse v2's callback needs the old langchain.callbacks layout.

LangGraph: the pipeline's skeleton

from langgraph.graph import StateGraph, START, END

g = StateGraph(State)
g.add_node("fetch_data", fetch_data)
...                                   # 5 nodes
g.add_edge(START, "fetch_data")
g.add_edge("fetch_data", "news_rag")  # a straight line
...
g.add_edge("explain", END)
agent = g.compile()

agent.invoke({"symbol": "AAPL", "as_of": day, ...})
  • A node is a plain function state → partial update; LangGraph merges the updates.
  • A node's name can't also be a state key: that's why the switch is use_news, not news, and llm_explanation, not explain.
  • No branches, loops or checkpoints are used; adding a conditional edge (e.g. skip news for crypto) is the natural next step if the graph grows.

LangChain: the two LLM calls

from langchain_openai import ChatOpenAI

class Sentiment(BaseModel):
    label: str        # bullish | bearish | neutral
    rationale: str

llm = ChatOpenAI(model="gpt-4.1-nano", temperature=0,
                 max_retries=6).with_structured_output(Sentiment)
out = llm.invoke(prompt, config=trace_config())
out.label  # a typed object, not free text
  • with_structured_output makes the model answer in the Pydantic schema, so no parsing of prose.
  • temperature=0: the same headlines classify the same way every run.
  • max_retries: 6 for the sentiment (it feeds the decision), 1 for the explanation (only prose; falls back to the rule text). The model comes from LLM_MODEL.
  • config={"callbacks": [langfuse]} sends each call to Langfuse when its keys are set.
Not LangChain on purpose: embeddings call the OpenAI SDK directly (text-embedding-3-small), and the vector store is ~130 lines of psycopg + pgvector instead of LangChain's PGVector wrapper, so the search can filter by symbol and date before ranking (see below).
05 · News RAG

Retrieval-augmented sentiment, without look-ahead

RAG = fetch relevant documents first, then let the LLM answer from them. Here the documents are news articles and the answer is one word: bullish, bearish or neutral.

The steps (news.py)

  1. Ingest: pull 7 days of news from every source with a key (Alpaca, paged; Polygon; Finnhub), keep only articles published before the decision moment (15:30 New York by default, or the bot's real time).
  2. Embed: only articles never seen before, into 1536-number vectors; re-running a window costs nothing.
  3. Store: one row per (article, symbol) in news on news-db.
  4. Retrieve: every article for the symbol in the window, with exact cosine similarity to “SYMBOL stock outlook, earnings, risks”.
  5. Re-rank: score = similarity × 0.5^(age / half-life). Half-life 36 h, but 168 h for earnings, guidance and M&A. Keep the top 8, each tagged with its age.
  6. Judge: the LLM labels the 8; a regex flags fresh (< 48 h) catalysts for the event strategies.

Design choices worth knowing

  • No vector index (HNSW/IVFFlat). The B-tree on (symbol, published_at) narrows to a few hundred rows first, then distance is exact. An approximate index filters after picking neighbours and can silently return too few.
  • Judged once, reused forever. Each (symbol, cutoff) judgment is saved in news_judgments (first write wins), so every backtest, comparison and restart sees the same news. Bump NEWS_JUDGMENT_VERSION after changing how news is judged.
  • A live bot's judgment is saved under its slot (10:00 or 15:30), so a later backtest of that day uses the exact news the bot traded on.
  • Failures degrade, never break. A source down → the others still count; the LLM rate-limited → “decided without news”; nothing incomplete is cached.

07 · Backtests

Four engines, one grading

The runner picks the engine from the strategy, the result goes through the same metrics and the same recommendation checklist (verdict.py).

Daily (simple.py)

  • Every rebalance_days: ask decision-service at the bot's slot, 15:30 and/or 10:00, replayed from 30-minute bars: backtest = bot.
  • Stops/targets checked on each stretch of the day; a gap fills at the open; both touched = the stop.
  • Slippage + fee on every fill, whole shares (coins in fractions), 20% drawdown breaker.

Intraday (intraday.py)

  • ORB, ICT sweep → FVG, ICT Power of 3 on 5-minute bars, one setup a day, flat by 15:55.
  • decision-service builds each day's plan bar by bar from finished bars only (no look-ahead).
  • Limit or market entries, risk-based sizing; futures as contracts with margin and per-contract fees.

Rotation (rotation.py)

  • Month-end momentum: hold the top N of a universe by 12-1 return (optionally only what rose).
  • Benchmark = the universe bought in equal parts on day one.
  • Runs straight on Yahoo closes; no decision-service calls.

Dip buyer (dip.py)

  • A watchlist checked every 5/15/30/60 min (or daily): buy a drop_pct fall under the window's high (by default once it turns up rebound_pct from its low), sell back at it; a stop sells and blacklists the symbol.
  • Each trade carries its chart points (the fall's high, the low, buy, sale); /runs/{id}/prices serves the prices around them.
  • Intraday bars from decision-service (5/15/30-min), each check on the bar that just closed; news verdicts from /news/sentiment only at a buy.
  • Benchmark = the watchlist bought in equal parts at the first check.

Scans

Symbols × strategies on a practice window; only the ones graded “Worth paper trading” sit an unseen exam window. 3 runs in parallel inside the service's 4 slots, each keeping only its last step in memory. The Scan page pools trades across symbols and counts twin ETFs once.

Live progress

POST /runs returns an id; the browser opens /ws/{id} and receives start / step / trade / done events as the engine emits them. A finished run's socket replays its events and closes.

08 · Live trading

The scheduler and the brokers

The full story is in the Trading Bot Lifecycle guide; the architecture in short:

Every 30 seconds, per bot (scheduler.py)

  1. Resolve orders still pending at the broker; keep the stop resting at the broker (Alpaca).
  2. Market hours: check the real account matches the bot's records.
  3. Every 5 min: refresh the price, record equity, enforce stop / target / drawdown breaker.
  4. At its slot (30 min after the open and/or before the close): ask decision-service and trade.

Restart-safe: “which slots are done” comes from the database, never from memory.

Brokers and safety

  • paper (built-in, Yahoo quotes) · alpaca-paper · alpaca-live, behind one Broker interface; live needs confirm_live.
  • Only one bot per symbol on a shared Alpaca account (a dip bot's whole watchlist counts); rotation and dip bots are paper-only.
  • Dip bots check at the end of each bar of their interval and post signals (down / rebound / up / stop / news) that the header's bell turns into pop-ups, desktop notifications, a sound or speech.
  • Sign-in: Argon2id passwords, a JWT in an HttpOnly cookie, admin approval for new users; nginx asks /auth/check before every API call.
  • Everything lands in trading-db: bots, decisions, orders, holdings, equity snapshots, an audit log.

10 · Harnesses

The code around the code

“Harness” means the scaffolding that runs something under control: the LLM inside the decision pipeline, the services inside tests, and the coding agent that built them.

The LLM harness

Everything around the two model calls: a fixed LangGraph order, a typed output schema, temperature 0, retries with backoff, a rule-text fallback, the judgment cache, a news cutoff that blocks look-ahead, and Langfuse tracing. The model is a small replaceable part; the harness makes it dependable.

The test harness

  • pytest per service, run in a throwaway container with the source mounted: make test.
  • Real Postgres, separate databases (news_test, trading_test): real data is never touched.
  • Fakes at the edges: FakeJudgments (no fake “bullish” ever reaches news-db), FakeBroker (fills, stops, misbehaviour on demand), scripted decide() functions for the engines, monkeypatched downloads.
  • ~480 tests: decision 193, backtest 118, trading 168; frontend type-checked with tsc.

The build harness

Built with Claude Code, a coding agent harness: a model plus tools to read and edit files, run shell commands and tests, drive a browser, and keep notes in a memory folder between sessions. Typical loop: edit → the backend hot-reloads → run the service's tests → call the API or run a scan to check real behaviour → rebuild the frontend.

11 · Facts & gotchas

Worth knowing before you change anything

Hot reload
Each backend's app/ folder is mounted and uvicorn runs with --reload. Saving a file there restarts that service: in-memory runs and scans are lost, so don't edit backtest-service while a long scan runs.
Frontend
A production nginx build, no hot reload. After changes: docker compose build frontend then docker compose up -d --no-deps --force-recreate frontend. Type-check with npx tsc -p tsconfig.json --noEmit --incremental false. vite.config.js shadows vite.config.ts in dev: edit both.
Secrets
decision-service/.env (OpenAI, Alpaca data/news, news keys) and trading-service/.env (Alpaca broker keys, JWT_SECRET). Read only when a container is created: recreate it after changing keys.
Databases
trading-db holds real history: never TRUNCATE it. make backup-trading-db snapshots it (last 30 days kept). New columns are added at startup by db._add_missing_columns().
Reproducible
Same settings → same result: saved news judgments, temperature 0, the 15:30 replay. Change how news is judged → bump NEWS_JUDGMENT_VERSION.
Time
Market logic runs in New York time (zoneinfo, tzdata pinned); this laptop is UTC+4. A year of timestamps mixes −04:00 and −05:00: parse with utc=True.
Symbols
App/Alpaca BRK.B ↔ Yahoo BRK-B; app/Yahoo BTC-USD ↔ Alpaca BTC/USD; ES in a backtest is the S&P future, on Alpaca it's a utility's stock; GOLD is a company, gold is GLD.
Speed
Technical-only decisions take ~10 ms (≈3.5 s per backtest-year); with news a decision takes seconds (fetch + embed + LLM), so screen with news off and re-check the finalists with news on.
Git
Never git stash in the main checkout: the hot-reloading containers would run the stashed state. No remote is configured.
Ports
8080 app · 8000/8001/8002 APIs · 5433 trading-db · 5434 news-db · 3000 Langfuse · 8082 GlitchTip · 5050 pgAdmin. All localhost-only.
12 · What the tests taught us

Findings from this app's own backtests

Not advice, just what the tools measured (Oct 2020 – Sep 2026 unless noted). They're the reason the app judges results with practice/exam windows and checklists instead of headline returns.

  • Holding is hard to beat. Over 6 years none of the daily strategies beat buy & hold on stocks, ETFs or gold (only on a bond fund that fell 42%, by losing less).
  • Winners don't repeat. Of 414 combinations, last month's top fifth did no better next month than the bottom fifth. None averaged even 5% a month.
  • Hindsight flatters. Rotating today's top 30 symbols made +1013%; the same rule on 2020's top 20 made +218% with a 46% drop.
  • More history humbles. Sector rotation looked great in 2023–26 (+99%) but over 2000–2020 made +267% vs +342% for holding the sectors: smaller crash losses, missed recoveries.
  • Costs decide intraday. ORB on TSLA: +321% at 0.01% slippage, +152% at 0.03%; ICT setups are rare and mostly unfilled at the gap's middle.
  • Realistic numbers: roughly 6–10% a year for stock strategies over the long run, with losing years.
  • A permanent blacklist kills a dip buyer. 5% fall / 5 days / 5% stop with symbols blacklisted for good: every symbol was blacklisted within about a year (sectors 2016–26: +7.5% vs +272% held). Letting symbols back and a 10% stop: +104% vs +105% in 2021–26, smoother, but +30% vs +82% in 2016–20.
